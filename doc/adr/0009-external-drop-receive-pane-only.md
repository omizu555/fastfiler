# ADR 0009: 外部 D&D 受信はペイン単位 (行レベル ドロップ非対応)

## ステータス

採用 (2026-05-23)

## コンテキスト

#D Phase 2 の受信側 (エクスプローラ等 → FastFiler) を実装するにあたり、
ドロップ先を「どこまで細かく判定するか」が論点となった。

内部 D&D (FastFiler 内のペイン間) では既に以下の階層で宛先を決めている:

1. フォルダ行 (一覧の特定の子フォルダ)
2. パンくず (上位フォルダ)
3. ペイン背景 (現在表示中のフォルダ)

外部 D&D の受信側でも同じ階層を実装するか、ペイン単位に絞るかを検討した。

## 検討した選択肢

### 案 A: ペイン単位のみ (採用)
- スクリーン座標から **どのペインの矩形に入っているか** だけを判定
- 宛先は常にそのペインの現在表示中フォルダ (`cur_path`)
- 各ペインは矩形 1 個を `RwSignal<HashMap<pane_id, Rect>>` に登録するだけ
- ハイライトはペイン全体の枠線色変更で済む

### 案 B: 内部 D&D と完全同等
- フォルダ行 / パンくず / 背景の優先順を外部にも適用
- virtual_list の数百行分の rect を追跡する基盤が必要
- COM スレッド (= UI スレッド) から `DragOver` で高頻度に hit-test 検索
- ハイライト対象が行単位になり、再描画範囲制御も繊細になる

## 決定

**案 A を採用する。**

## 理由

- 外部 D&D の主ユースは **他アプリ → FastFiler への持ち込み**。
  ユーザーは「宛先フォルダをまず開いてから落とす」操作が自然
- フォルダ行への直接ドロップが必要なら、まずそのフォルダを開けばよい
  (操作量は 1 クリック増えるだけ)
- 行レベル rect の追跡は virtual_list の仮想化と相性が悪く、
  実装複雑度・性能リスク・バグリスクが大幅に増える
- ハイライト UI もペイン枠 1 個で済み、Q4 で決定した「signal 直接更新 +
  行スタイル単位購読」アーキテクチャが単純なまま保てる

## 影響

- `CONTEXT.md` に「ドロップゾーン」用語を追加 (外部 D&D 受信時のペイン単位の宛先)
- 内部 D&D の挙動には影響しない (今まで通り行/パンくず/背景の優先順)
- 後から行レベルに広げる場合は rect 管理基盤の追加 + 本 ADR の改訂が必要
